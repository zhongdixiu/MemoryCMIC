LLM 抽取、真实 Embedding 服务或 Agent 授权控制面。

## 2. 进展维护规则

每次完成一个可独立验证的工作批次后，必须同步更新本文档：

1. 更新“当前进展总览”中的状态和完成日期；
2. 在对应阶段记录实际交付物、执行命令和验证结果；
3. 记录实现与冻结设计的偏差、未决问题及阻塞；
4. 明确下一阶段及其开始条件；
5. 只有代码或 migration 已实际执行且验收项通过，才能标记为“已完成”；
6. 部分完成时保持“执行中”，不得用计划内容代替实际结果；
7. 发生 No-Go 条件时停止扩大实现范围，先记录问题和最小修订建议。

状态定义：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚未进入实施 |
| 执行中 | 已开始，但阶段验收未全部通过 |
| 已完成 | 交付物已落地，阶段检查全部通过 |
| 阻塞 | 因外部依赖、权限或输入缺失无法继续 |
| 需修订 | 验证发现冻结模型存在结构性问题，需先完成设计决策 |

## 6. 第二批：样例数据与最小领域函数

状态：未开始

### 6.1 实施范围

- 准备两个租户、两个用户、一个 Agent、一个 company 的虚构样例；
- 覆盖 email、disk、communication 三个业务域；
- 覆盖 project_a、project_b、project_c 三个项目域；
- 实现范围数组的去重和稳定排序；
- 实现以下最小函数，不扩展为完整 Service 或 HTTP API：

```text
create_source
update_or_invalidate_source
create_memory
add_evidence_group
recheck_downstream
invalidate_memory
create_or_replace_profile
enqueue_task
search_memories
```

- 实现确定性 1536 维假向量生成器，不调用外部 Embedding 服务。

### 6.2 验收标准

- 样例数据全部为虚构内容；
- 相同输入文本与 `model_id` 生成相同向量；
- 数组写入前完成去重、排序，空数组仍由数据库拒绝；
- evidence group 不能跨下游对象复用；
- 写入事务能够同时保存业务实体、任务和审计；
- 单元测试互相隔离且不依赖执行顺序。

### 6.3 停止条件

- 最小函数需要改变冻结字段含义；
- evidence group 单下游规则无法稳定校验；
- 事务边界无法同时覆盖业务实体、任务和审计。

## 7. 第三批：证据组与生命周期

状态：未开始

### 7.1 实施范围

- OR：多个独立证据组；
- AND：同一证据组包含多个共同依据；
- 多事实共同支撑推断；
- 记忆到画像的 `profile_basis`；
- 来源失效、记忆失效、TTL、纠正、替代和争议；
- 下游递归检查、画像重建及向量删除任务创建。

### 7.2 验收标准

- 完整性判断遍历 evidence group 的全部历史组成边；
- 完整边必须同时满足边有效、上游有效、版本一致且未过期；
- 任一完整组存在时下游可以继续有效；
- 所有组均不完整时下游立即停止在线使用；
- TTL 到期任务未执行时，在线检索仍能立即排除；
- 完成冻结用例 T01～T07、T09、T15、T16。

### 7.3 No-Go 条件

- AND/OR 充分性语义无法稳定实现；
- 来源失效后仍能通过正常检索获得依赖记忆；
- 依赖传播必须结构性修改冻结模型才能实现。

## 8. 第四批：PostgreSQL 异步任务队列

状态：未开始

### 8.1 实施范围

- 任务幂等入队；
- `priority`、`available_at` 调度；
- `FOR UPDATE SKIP LOCKED` 并发领取；
- `worker_id`、`locked_until` 租约和续租；
- 失败重试、退避、过期租约接管；
- 任务完成时的 Worker 所有权检查；
- `input_version` 防止旧结果覆盖新版本；
- `correlation_id` 在任务和审计链路中传播。

### 8.2 验收标准

- 两个独立数据库连接不会领取同一任务；
- 未过期租约不能被其他 Worker 接管；
- 租约过期后可以安全接管；
- 原 Worker 失去租约后不能完成任务；
- 优先级领取顺序为 100、50、0；
- 未来 `available_at` 任务不能提前领取；
- 旧版本任务更新影响 0 行；
- 完成冻结用例 T10、T12、T17～T19。

## 9. 第五批：范围、向量检索与性能冒烟

状态：未开始

### 9.1 实施范围

- 租户、状态、TTL、业务域和项目域过滤；
- 用户记忆、Agent 经验、company 公共规则三路召回；
- 指定 `model_id` 的向量检索；
- `content_hash` 不一致的 stale 向量排除；
- 至少一万条虚构记忆和向量的轻量性能冒烟；
- 记录代表性查询的 `EXPLAIN (ANALYZE, BUFFERS)`。

### 9.2 验收标准

- 完成冻结用例 T08；
- `invalidated`、`disputed`、`expired` 记忆不返回；
- 无项目上下文时不返回受项目限制的记忆；
- 三路主体分别过滤后再合并；
- 记录 p50、p95 和索引使用情况；
- 出现明显全表扫描时给出原因和最小调整建议。

## 10. 第六批：Honcho Profile 与迁移验证

状态：未开始

### 10.1 开始条件

- `HONCHO_DATABASE_URL` 使用只读账号；
- 实际 Honcho DDL 可读取；
- 目标库 migration 和核心约束保持稳定；
- 明确 `observer/observed` 到新系统 `subject` 的映射规则。

### 10.2 实施范围

- `profile`：只读统计源库结构和数据分布；
- `dry-run`：生成映射计划，不写目标库；
- `migrate`：迁移代表性小批次；
- `validate`：执行数量、来源、证据和幂等对账；
- 旧向量、queue 和锁状态不迁移；
- 缺失来源使用明确标记的 `legacy_import` 合成来源，不伪造消息关系。

### 10.3 验收标准

- Honcho 源库无任何写入；
- 第二次迁移新增 source、memory 和 evidence 均为 0；
- 目标实体和 `external_entity_mapping` 在同一事务写入；
- 不存在悬空 evidence；
- 无法识别的主体和缺失来源都有数量及样例报告；
- 完成冻结用例 T13、T14。

### 10.4 停止条件

- 只能获得具有写权限且无法限制的 Honcho 连接；
- 实际 DDL 与预期存在无法解释的重大差异；
- 主体语义或来源关系存在大规模无法解释的映射；
- 重复迁移产生重复数据。

## 11. 第七批：综合验收与 Go/No-Go

状态：未开始

### 11.1 最终检查

- 冻结版 T01～T19 全部执行；
- 补充数据库约束测试全部执行；
- migration、生命周期、任务队列、检索和迁移结果可复现；
- 汇总查询计划和轻量性能结果；
- 更新设计偏差、未决问题和剩余风险；
- 生成最终 Markdown 报告及 `validation_results.json`。

### 11.2 GO 条件

- 数据库能够拒绝跨租户和非法关系；
- AND/OR evidence group 语义稳定；
- 无在线失效数据泄漏；
- 旧任务不能覆盖新版本；
- 任务幂等、优先级和租约行为正确；
- Honcho 映射可解释，重复迁移新增记录为 0；
- 冻结模型不需要结构性重构。

全部满足时，结论为：

```text
GO：数据模型 V1.0 可进入统一记忆服务核心功能开发。
```

### 11.3 NO-GO 条件

出现以下任一情况时，不继续扩大核心服务开发：

- 无法通过数据库约束阻止跨租户证据关系；
- evidence group 无法表达冻结的 AND/OR 充分性；
- 来源失效后相关记忆仍能正常检索；
- 旧异步任务能够覆盖新版本；
- Honcho 主体或来源关系存在大规模无法解释的映射；
- 重复迁移产生重复数据；
- 核心字段必须结构性重构。
